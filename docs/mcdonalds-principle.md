# 맥도날드 원칙 - AI 시대의 개발 매뉴얼

> 출처: 삼양식품 테크리드 김성준 - "바이브 코딩 시대의 개발 매뉴얼"
> https://yozm.wishket.com/magazine/detail/3457/

---

## 한 줄 요약

> "맥도날드에서 일하는 분들은 전문 셰프가 아니지만, 전국 어디서나 훌륭한 햄버거가 나온다."

AI 에이전트(알바)가 바뀌어도, 매뉴얼만 읽으면 동일한 품질의 코드가 나오는 시스템을 만드는 것.

---

## 배경: 왜 이 원칙이 필요한가

### 초기 성공
삼양식품 테크리드 김성준은 3명(PM, 디자이너, 엔지니어) 팀으로 AI 에이전트(Cursor, Claude)를 활용해
5개월 만에 Popow.ai를 정식 출시했다. 초기 전제조건 3가지:

1. **모든 정보를 리포지토리에 기록**
2. **언제든 질문에 답할 수 있는 시스템**
3. **빠른 수정과 배포 환경**

### 규모 확장 후 문제 발생
프로젝트가 커지면서 "괴물 같은" 결과물이 나타났다:

- AI 할루시네이션 (없는 API를 만들어냄)
- 의도 불명확한 코드 생성
- 중복 API 개발
- DB에 없는 정보를 억지로 표시

### 근본 원인: 컨텍스트 과부하
Claude.md(AI 룰 파일)가 **2,000줄을 초과**하면서
AI 세션 시작시 컨텍스트의 30%가 이 룰 파일로 채워졌다.

결과적으로:
- 코드만 남고 "왜 이 코드를 작성했는지" 의도가 사라짐
- 매번 최신 공식 문서 전체를 조회하는 비효율 발생
- AI가 이전 작업과 모순되는 코드를 생성

## 핵심 비유: 맥도날드 프랜차이즈

전문 셰프 없이도 전국 어디서나 일관된 햄버거가 나오는 비결은 **매뉴얼**이다.

| 맥도날드 | AI 개발팀 |
|----------|-----------|
| 본사 | 테크리드 (매뉴얼 = CLAUDE.md 작성) |
| 지점장 | PM/디자이너/사용자 (요구사항 정의, 의사결정) |
| 알바 | AI 에이전트 (Cursor, Claude 등 실제 코드 작성) |
| 매뉴얼 | 프로젝트 룰 파일 + 기획서(PRD) |

**핵심 포인트**: 알바가 매일 바뀌어도 매뉴얼만 읽으면 같은 품질이 나와야 한다.
AI도 마찬가지다. 컨텍스트가 리셋되어도, 문서만 읽으면 같은 코드가 나와야 한다.

## 3대 운영 원칙

### 원칙 1: 컨텍스트 최소화

> "에이전트가 켜지면 200줄 내외의 핵심 가이드만 읽고 바로 일을 시작해야 합니다."

**문제**: 룰 파일이 2,000줄이면 AI가 읽다가 중요한 내용을 놓친다.
**해결**: 핵심 가이드를 200줄 이내로 유지한다.

적용 방법:
- 메인 가이드(CLAUDE.md)는 **200줄 내외**로 유지
- 200줄 초과시 반드시 **분할**
- 부족한 정보는 **어펜딕스(Appendix)** 형태로 별도 문서에 작성
- 각 가이드에 어펜딕스 참조 경로를 명시

```
CLAUDE.md (200줄 - 핵심만)
├── docs/api-spec.md         (필요할 때만 참조)
├── docs/kafka-events.md     (필요할 때만 참조)
└── docs/db-schema.md        (필요할 때만 참조)
```

### 원칙 2: 컨텍스트 망각 (Context Amnesia)

> "리포지토리에 남지 않는 정보는 휘발되어도 되는 정보"

**문제**: 채팅에서 "아 그거 이렇게 하자"라고 말했는데, 다음 세션에서 AI가 모른다.
**해결**: 중요한 결정은 반드시 코드 또는 문서에 남긴다.

판단 기준:
```
채팅에서만 존재하는 정보 → 휘발되어도 OK (잘못된 업무)
리포지토리에 기록된 정보 → 영구 보존 (올바른 업무)
매번 재설명이 필요한 정보 → 문서화 필요 (잘못된 업무)
```

적용 방법:
- 하나의 업무가 끝나면 컨텍스트는 **의도적으로 잊혀진다**
- AI 세션이 리셋되어도 문제없도록 설계
- "이전 대화에서 말했잖아"는 존재하지 않는다
- 중요한 결정은 코드, 커밋 메시지, 문서에 기록

### 원칙 3: 의도와 결정 기록

> 코드가 "무엇(What)"을 하는지가 아니라 "왜(Why)" 이 결정을 했는지 기록

**문제**: 코드는 있는데 왜 이렇게 짰는지 아무도 모른다.
**해결**: 바이브 코더(사용자)는 항상 Why를 기록한다.

기록해야 하는 것:
- **선택의 이유**: 여러 해결책 중 왜 이걸 골랐는지
- **장단점**: 선택한 방안과 버린 방안의 트레이드오프
- **우선순위**: Must / Should / Could / Won't 구분

나쁜 예:
```
"로그인 기능 구현해줘"
```

좋은 예:
```
"로그인 기능 구현해줘.
- Must: 이메일 + 비밀번호 인증
- Should: 소셜 로그인 (Google)
- Won't: 생체 인증 (이번 버전 제외)
- 배경: 최근 리팩토링으로 기존 로그인 코드가 복잡해져서 단순화 필요"
```

## PRD 7단계 워크플로우

기획서(PRD) 작성 프로세스. 이 과정을 거쳐야 AI가 "괴물"을 만들지 않는다.

```
1. 컨텍스트 확보     → 현재 코드/시스템 상태 파악
2. 요구사항 정의     → Goal / Non-Goal 명확히
3. UX 설계          → 사용자 흐름, 화면 설계
4. 의존성 분석       → 기존 코드, 외부 라이브러리, DB 변경
5. 구현 계획 작성    → 작업 목록 + MoSCoW 우선순위
6. 리스크 분석       → 실패 시나리오, 보안 이슈
7. 테스트 작성       → 검증 기준 정의
```

### MoSCoW 우선순위

AI에게 단순 기능 리스트를 던지면 안 된다. 우선순위를 명확히 분류해야 한다.

| 레벨 | 의미 | AI에게 지시 |
|------|------|-------------|
| **Must** | 없으면 릴리스 불가 | "반드시 구현. 이것 없이 PR 올리지 마" |
| **Should** | 중요하지만 필수 아님 | "가능하면 구현. 시간 부족하면 다음에" |
| **Could** | 있으면 좋음 | "여유 있으면. Must/Should 먼저" |
| **Won't** | 이번 버전 제외 | "절대 건드리지 마. 범위 밖" |

Won't가 중요한 이유:
AI는 "더 좋게 만들어주려고" 범위 밖 기능을 멋대로 추가하는 경향이 있다.
Won't를 명시하면 이걸 방지할 수 있다.

## 실행 방법: 녹음 → AI 문서화

팀의 구체적 실행 방식:

```
1. 모든 회의를 녹음한다
2. AI에게 요청: "우리가 회의에서 이 결론을 도출한 과정을 스크립트로 작성해줘"
3. AI가 초안을 작성한다
4. 사람이 Goal / Non-Goal을 정의하며 검토한다
5. 최종 기획서(PRD) 완성
```

기존 워크플로우를 버리지 않는다. AI가 **문서화를 도와주는 것**이지, 사람의 판단을 대체하는 게 아니다.

---

## 성과

> "기획서만 충분히 작성되면 뒷단은 정말 마법같이 잘 풀리는 경험"

- **Before**: 2주 걸리던 피처
- **After**: 1일 만에 완성

핵심은 코딩 속도가 빨라진 게 아니라, **기획의 품질이 올라가서** AI가 제대로 된 코드를 만들어낸 것이다.

---

## 핵심 철학

> "AI가 대체할 수 있는 부분은 과감히 녹여내고,
> 우리가 기존에 잘 동작시켰던 방식의 본질은 살리는 것"

맥도날드 원칙은 새로운 발명이 아니다.
소프트웨어 공학에서 오래전부터 존재하던 원칙들을 AI 시대에 맞게 재해석한 것이다:

- 문서화 → AI가 읽을 수 있는 형식으로
- 코드 리뷰 → AI가 룰을 자동 적용
- 기획서 → AI가 실행할 수 있는 수준의 구체성으로
